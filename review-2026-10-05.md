Проверка Converter для Au+Au при √sNN = 3 ГэВ, 5 октября 2026 года.

Это отчёт об исходной ревизии `bf4db0e`. После проверки конвертер исправлен; актуальные определения, формат выхода и команды проверки описаны в `README.md`. Приведённые ниже строки кода и результаты относятся к состоянию до исправлений.

**Вывод: восстановление последней точки взаимодействия в целом соответствует заданному каскадному режиму SMASH. Определение спектатора соответствует транспортному критерию «не было ни одного взаимодействия», но не стандартному неупругому определению участника в MC Glauber. Отбор событий и запись Npart содержат ошибки.**

Проверены `src/OscarConverter.cpp`, `src/Particle.cpp`, определения McDst в соседнем `sthbtmaker`, передача координат в StHbtMcDstReader, создание пар в StHbtAnalysis, настройки `hbt_auau_simu.cxx` и чтение корреляционных гистограмм в `cf_maker`. Исходная ревизия Converter: `bf4db0e`. Для запуска проверки использованы ROOT 6.40.02 и настоящие классы McEvent/McParticle/McRun с новым локальным ROOT-словарём; лежащая в соседнем проекте библиотека McDst собрана под Linux и для macOS не подходит.

Конфигурация пользователя: 197 нуклонов в каждом ядре, 79 протонов и 118 нейтронов; CM frame; Fermi_Motion=frozen; End_Time=200 fm/c; Delta_Time=0.1 fm/c; Force_Decays_At_End=true; полная история OSCAR2013 с начальным и конечным списками. Данных реальной генерации и номера версии SMASH нет. Ниже сравниваются определения и поведение программы, а не измеренное согласие распределений.

**Определения участников и спектаторов.** Обозначим множество начальных ID через I₀, а множество ID из всех блоков interaction через H. Условие в `src/OscarConverter.cpp:238` выделяет I₀\H: начальный нуклон не встретился ни в одном взаимодействии за всю эволюцию. Для данного Au+Au порог ID<394 соответствует начальной нумерации SMASH: счётчик начинается с 0 после reset и растёт при создании новых частиц ([исходник SMASH](https://github.com/smash-transport/smash/blob/SMASH-3.0/src/particles.cc)). Надёжнее получать I₀ из блока in, а не из константы.

| Ситуация для начального нуклона | Классификация этого кода | Стандартный MC Glauber с σNN,inеl |
| --- | --- | --- |
| Ни одного взаимодействия | Спектатор | Спектатор, если геометрически не получил неупругого NN-столкновения |
| Только упругие NN-столкновения | Участник транспорта | Не становится участником по неупругому критерию |
| Неупругое NN-столкновение с противоположным ядром | Участник транспорта | Участник геометрического расчёта |
| Был затронут только вторичным πN-рассеянием | Участник транспорта | Вторичные πN-рассеяния отсутствуют в стандартной геометрической модели |

Таблица сравнивает критерии; траектории и набор столкновений двух моделей не обязаны совпадать. В стандартном MC Glauber участник — исходный нуклон, имеющий хотя бы одно неупругое NN-столкновение, Ncoll — число таких бинарных столкновений. Геометрический вариант использует прямые траектории и условие d⊥²≤σNN,inel/π. Для Au+Au Nspec=394−Npart при одном согласованном определении обоих чисел. См. [обзор Miller et al., разделы 2.4 и 4](https://arxiv.org/html/nucl-ex/0701025v1).

Называть транспортное определение ошибкой само по себе нельзя. Однако подставлять полученное число в сравнение со стандартным Glauber как ту же величину нельзя. При √sNN около 3 ГэВ упругие процессы и последующая динамика существенны; различия транспортного и глауберовского Npart особенно важны. Это обсуждается в [исследовании Kuttan et al.](https://link.springer.com/article/10.1140/epjc/s10052-023-11968-z); его численные результаты относятся к другим заданным в статье условиям и здесь не используются как эталон вашего SMASH.

**P1 — Npart всегда записывается нулём.** В `src/OscarConverter.cpp:161` одна переменная nPart используется для in, out и end. В стандартном старом заголовке `# event 0 end 0 impact ...` она получает служебный 0. Именно он передаётся в processEvent на строке 191 и в setNpart на строке 52. По `McEvent.h:73` это число участников, а не конечная множественность. Ncoll не задаётся и остаётся −1. Даже сохранение значения из out не исправит физический смысл поля: нужно отдельно считать уникальные начальные нуклоны по выбранному определению. По этим ROOT-полям сейчас сравнение Npart(b), Ncoll(b) с Glauber невозможно.

**P1 — конечная множественность 394 не доказывает упругость.** Строки 171–174 и 190–193 целиком удаляют такие события. Неупругий канал NN→NΔ с последующим NΔ→NN возвращает прежнее число частиц; отсутствие конечного пиона не означает отсутствие неупругой истории. В вашем конфиге Force_Decays_At_End не отменяет этот пример, если резонанс был поглощён раньше конца эволюции. Из-за этого отбор задаёт зависимость от конечного состояния и может менять центральность принятой выборки.

`scattering_projectile_target yes` означает, что взаимодействовали projectile и target, включая упругий процесс. Комментарии строк 183–185 о рождении новых частиц неверны. В исходнике SMASH флаг выставляется при наличии входящих частиц обоих ядер без проверки упругости; затем он печатается в OSCAR ([experiment.h](https://github.com/smash-transport/smash/blob/SMASH-3.0/src/include/smash/experiment.h), [oscaroutput.cc](https://github.com/smash-transport/smash/blob/SMASH-3.0/src/oscaroutput.cc)). Для транспортной выборки взаимодействовавших событий можно использовать этот флаг. Для выборки, соответствующей неупругому определению Glauber, требуется отдельная проверка истории и типов процессов.

**Сохранение координат последнего взаимодействия.** Для полного full_event_history, стабильных начальных нуклонов и каскада без потенциалов логика map[ID] разумна: SMASH печатает сначала входящие, затем выходящие частицы каждого взаимодействия; последнее выходящее состояние пережившего ID остаётся в карте. Конечный out выбирает только дожившие частицы. На примере пиона, родившегося при t=10 и рассеявшегося при t=20, ROOT содержит t=20 и координату последнего рассеяния, а не координату свободного пролёта при t=200. Числовые единицы OSCAR и McParticle совместимы: fm и GeV; StHbtMcDstReader передаёт их в emissionPoint напрямую.

В строке 247 заменяется вся частица, включая импульс, а не только координаты. Для указанного каскада без потенциалов это допустимо после последнего столкновения. При изменении режима на движение в потенциалах такое равенство импульса с конечным состоянием уже требует отдельной проверки.

**P2 — отсутствие истории частицы молча превращает её в фиктивную частицу.** `interactions[p.ID]` создаёт Particle по умолчанию при отсутствии ключа. В выходе появляются PDG=0, нулевая энергия и t=−1. При вашей полной истории это не должно происходить для созданной частицы, поэтому отсутствие записи должно быть диагностируемой ошибкой. Проверка на синтетическом неполном входе воспроизвела этот результат. Также отсутствуют проверки числа строк блока, успешности извлечения полей и незавершённого события при EOF.

**Маркировка спектатора.** `Particle::SetSpectator()` ставит t=x=y=z=−999; это условная метка, не физическая точка. StHbtMcDstReader не исключает её явно. В вашем анализе π± начальные нуклоны удаляются PDG-cut, поэтому эта метка сама по себе не портит пионный emissionPoint. Для корреляций протонов потребуется явный отбор по статусу спектатора. Предпочтительно сохранять координаты и отдельный физический статус, а не кодировать статус координатами.

**Force_Decays_At_End и HBT.** Опция заставляет оставшиеся резонансы распасться после последнего шага ([документация SMASH](https://theory.gsi.de/~smash/userguide/3.1/doxypage_input_conf_collision_term.html)). В проверенном исходнике SMASH 3.0 финальный DecayAction создаётся с нулевым дополнительным временем, то есть в точке конца эволюции ([decayactionsfinder.cc](https://github.com/smash-transport/smash/blob/SMASH-3.0/src/decayactionsfinder.cc)). Конвертер честно сохранит такие точки для дочерних пионов; это не дефект парсинга. Их физическая интерпретация зависит от процедуры моделирования оставшихся распадов. Для HBT полезны отдельный учёт таких дочерних частиц и проверка устойчивости результата к End_Time. Глауберовская геометрия сама по себе не задаёт точки кинетического freeze-out и не предсказывает эти корреляционные функции.

**Смешивание и определение корреляционной функции.** В Converter смешивания нет. В соседнем `sthbtmaker` StHbtAnalysis создаёт реальные пары внутри текущего события, смешанные — с предыдущими, затем добавляет текущее событие в буфер (`StHbtAnalysis.cxx:639–685`); самосмешивание в этом фрагменте исключено.

В `hbt_auau_simu.cxx:382–386` заданы один impact-bin, один vertex-bin и глубина смешивания 1. Отдельный экземпляр анализа и event cut создаются для каждого диапазона центральности, поэтому разные диапазоны центральности в один буфер здесь не попадают. Однако более узкого разбиения по b внутри диапазона нет. Глубина 1 допустима; статистическую устойчивость и адекватность широких диапазонов для mixed reference надо оценивать по данным, если этот reference используется.

Для показанного kT-анализа `StHbtModelBPLCMS3DCorrFctnKt.h:46` задаёт `isFillDenominators=false`, main не переопределяет аргумент, а `addMixedPair` заполняет гистограммы только при true. `cf_maker/src/io/input.cpp:63–71` читает num и num_wei. Следовательно, фактическая оценка:

    C_model(q) = Σ_same w(q) / N_same(q).

Это допустимая оценка среднего фемтоскопического веса. Её нужно отличать от экспериментального отношения нормированных same-event и mixed-event распределений:

    C_mixed(q) = normalization × A_same(q) / B_mixed(q).

Отсутствие mixed reference не является ошибкой для первого выбранного определения, но утверждение, что текущая kT-функция вычисляется через смешивание, не соответствует цепочке кода. Замена знаменателя изменит измеряемую величину и потребует отдельной проверки нормировки и остаточных корреляций.

**Центральность.** Границы b=4.6, 8.0, 10.4, 13.1 fm помечены как 10%, 30%, 50%, 80% при σNN=28 mb (`hbt_auau_simu.cxx:57–61`), однако происхождение калибровки в доступном коде не задано. Одного комментария недостаточно для подтверждения этих процентов. При выборке с плотностью генерации p(b)∝b процентили по b относятся к интегралу 2πb P_AA,inel(b), а не ко всем сгенерированным пролётам. Отбор по конечной множественности задаёт другую вероятность принятия; после его исправления границы нужно проверить заново. Настройки ядерной плотности, σNN и определения принятого события должны совпадать в сравниваемых расчётах.

**P1 при SMASH ≥3.2 — новый заголовок не читается.** Начиная с 3.2 в OSCAR добавлено поле ensemble ([официальный changelog](https://theory.gsi.de/~smash/doc/3.4/md_CHANGELOG.html)). Строка `# event 0 ensemble 0 out 395` приводит этот парсер в SkipEvent; строка end также не распознаётся. Контрольный пример с такими заголовками создаёт ROOT с нулём событий и exit code 0. Актуальность для ваших файлов зависит от версии SMASH.

**Дополнительная проблема метаданных.** `child={−1,1}` в строке 31 записывает всем частицам одинаковый индекс последнего ребёнка 1; реальные родственные связи не восстановлены. OSCAR ID заменяются произвольным последовательным idx из unordered_map. Эти поля не подходят для отслеживания потомков исходных нуклонов или распадного происхождения. Для сравнения участников после преобразований NN→NΔ и распадов нужно явно хранить происхождение, а неизвестные связи кодировать корректными значениями отсутствия.
